# Agent.md — 天氣現象與氣象變化百科

## 1. 專案目的

本專案是一個介紹天氣現象與氣象變化的百科網站，主要以台灣常見的天氣現象為主，搭配一般氣象知識，讓使用者了解不同天氣的特徵、形成原因，以及發生前可能出現的氣象變化。

本網站的定位是「氣象知識百科」，而不是即時天氣查詢或天氣預報系統。

### 核心目標

- 介紹常見天氣現象及其形成原因。
- 說明天氣發生前可能出現的氣象徵兆。
- 整理相關雲種、氣壓、溫度、濕度及風向等資訊。
- 透過閱讀式介面，讓使用者逐步了解氣象知識。
- 提供雲種圖鑑，方便使用者認識不同雲種。

### 網站不包含的功能

- 即時天氣查詢。
- 天氣預測。
- 即時氣象 API。
- 使用者登入及帳號系統。
- 資料庫與後端服務。
- 收藏、測驗及其他未規劃的互動功能。

## 2. 技術架構

目前採用原生前端技術：

- HTML：網頁結構。
- CSS：頁面樣式、排版及響應式設計。
- JavaScript：頁面切換、資料管理及動態內容呈現。

不使用 React、Vue 等前端框架，也不需要後端伺服器。

### 目前主要檔案

```text
專案根目錄/
└── index.html
```

目前 HTML、CSS、JavaScript 都集中在 `index.html`：

- `<head>`：網頁基本設定。
- `<style>`：網站 CSS 樣式。
- `<body>`：網頁主要結構。
- `#app`：JavaScript 動態渲染內容的主要容器。
- `<script>`：資料定義及互動功能。

主要 JavaScript 資料與函式包括：

- `weatherData`：天氣分類及各天氣的介紹資料。
- `chapters`：天氣介紹章節。
- `clouds`：雲種圖鑑資料。
- `showHome()`：顯示首頁。
- `openWeather()`：開啟指定天氣介紹。
- `renderReader()`：渲染閱讀頁面。
- `goChapter()`：跳轉至指定章節。
- `changeChapter()`：切換上一頁或下一頁。
- `showClouds()`：顯示雲種圖鑑。

修改時應優先沿用目前的架構及函式，不要在沒有必要的情況下重新設計整個系統。

## 3. 網站整體風格

### 視覺定位

採用「現代氣象資訊風格」。

整體設計應呈現清楚、簡潔、具有科普網站的專業感，避免過度裝飾或過多動畫。

### 配色原則

全網站使用統一配色，不因天氣種類而切換整體主題。

建議以以下色系為主：

- 深藍色：標題、主要文字及重要資訊。
- 藍色：按鈕、連結及互動元素。
- 白色：主要背景及內容卡片。
- 淺灰色：次要背景及區塊分隔。

### 圖片與圖示

- 使用適合的真實天氣照片呈現不同天氣。
- 雲種圖鑑應搭配雲種圖片。
- 圖示應簡潔且容易辨識。
- 圖片需與實際介紹內容相符。
- 不應使用容易造成錯誤氣象觀念的圖片。

### 響應式設計

網站應支援桌面及手機瀏覽：

- 桌面版：維持清楚的內容層次及閱讀寬度。
- 手機版：卡片及內容區塊改為適合窄螢幕的排列方式。
- 閱讀頁面：保留觸控左右滑動功能。

## 4. 頁面結構

網站主要分為首頁、天氣介紹頁及雲種圖鑑。

### 4.1 首頁

首頁採用大型主視覺搭配分類卡片。

由上而下包含：

1. 導覽列
   - 網站名稱或 Logo。
   - 首頁入口。
   - 天氣百科入口。
   - 雲種圖鑑入口。

2. 主視覺區
   - 天空或天氣相關背景圖片。
   - 網站名稱。
   - 網站簡介。
   - 進入百科按鈕。

3. 網站簡介
   - 說明網站用途及介紹範圍。

4. 天氣分類卡片
   - 展示八種天氣分類。
   - 點擊卡片後進入對應介紹頁。

5. 天氣小知識
   - 提供簡短的氣象知識。

6. 雲種圖鑑入口
   - 引導使用者前往雲種介紹頁。

7. 頁尾
   - 網站名稱。
   - 資料來源或相關說明。

### 4.2 天氣介紹頁

目前規劃八種天氣：

1. 晴天
2. 陰天
3. 降雨
4. 雷雨
5. 颱風
6. 濃霧
7. 強風
8. 寒流

每種天氣均包含六個介紹區塊：

| 章節 | 內容 |
|---|---|
| 天氣介紹 | 天氣特徵、外觀及常見情況 |
| 發生前的氣象徵兆 | 雲種、氣壓、溫度、濕度、風向及風速等變化 |
| 天氣形成原因 | 說明主要氣象原理 |
| 天氣變化流程 | 從形成前到天氣發生的變化過程 |
| 雲種介紹 | 相關雲種、外觀及氣象意義 |
| 相關知識與注意事項 | 延伸知識、生活影響及安全提醒 |

各天氣的六個章節都應保留，但實際內容可以依照天氣特性調整，不必強制使用完全相同的描述方式。

### 4.3 閱讀頁面操作

- 使用水平左右滑動方式切換章節。
- 顯示目前章節頁數，例如 `2 / 6`。
- 提供上一頁及下一頁按鈕。
- 提供章節目錄，可直接跳轉至指定章節。
- 支援手機觸控左右滑動。
- 切換時應維持平滑的過場效果。

### 4.4 雲種圖鑑

雲種圖鑑為獨立內容頁。

每種雲應包含：

- 雲種名稱。
- 雲種圖片。
- 外觀特徵。
- 常見高度或分類（適用時）。
- 形成條件。
- 相關氣象意義。

內容應以容易理解的科普說明為主。

## 5. 新增天氣內容時的格式

新增天氣資料時，必須沿用現有 `weatherData` 的資料結構，不應隨意更改欄位名稱。

目前資料概念如下：

```javascript
{
    name: "天氣名稱",
    icon: "天氣圖示",
    desc: "簡短介紹",
    intro: "天氣詳細介紹",
    signs: "發生前的氣象徵兆",
    cause: "天氣形成原因",
    steps: "天氣變化流程",
    clouds: "相關雲種介紹"
}
```

若目前程式碼已有額外欄位，例如相關知識或注意事項，新增內容時必須沿用原本欄位，不可直接刪除或替換。

### 內容撰寫原則

1. 使用繁體中文。
2. 採用一般民眾容易理解的科普語氣。
3. 專業術語第一次出現時，應提供簡單解釋。
4. 內容應有足夠資訊，但避免重複敘述。
5. 不要只列出名詞，應說明其與天氣現象的關係。
6. 不同天氣應有符合自身形成機制的介紹。
7. 不應為了讓內容看起來完整而加入不相關資訊。

### 氣象徵兆的描述格式

介紹天氣發生前的變化時，可依照實際情況整理：

- 雲種：可能出現哪些雲，以及其代表的氣象意義。
- 氣壓：氣壓可能上升、下降或維持穩定。
- 溫度：溫度可能升高、降低或出現明顯變化。
- 濕度：空氣中的水氣含量及相對濕度變化。
- 風向與風速：風向轉變、風速增強或減弱。
- 其他現象：依照該天氣的形成機制補充。

不需要每種天氣都包含上述全部項目，應以實際相關性為準。

## 6. 新增雲種資料時的格式

新增雲種時，沿用目前 `clouds` 陣列的資料結構。

基本內容應包含：

```javascript
{
    name: "雲種名稱",
    image: "圖片路徑",
    description: "外觀及特徵",
    meaning: "相關氣象意義"
}
```

若現有程式碼使用不同欄位名稱，應以實際程式碼為準，不要為了符合範例而更改既有資料結構。

### 雲種內容原則

- 使用正式且正確的雲種名稱。
- 外觀描述應能幫助使用者辨認。
- 氣象意義應說明可能代表的天氣變化。
- 不應將雲種直接視為必然發生某種天氣的判斷依據。

## 7. 檔案命名與放置規則

目前專案採用單檔架構，因此新增功能時應優先沿用 `index.html`。

若未來因內容或圖片數量增加而需要拆分檔案，應採用清楚且一致的命名方式。

建議結構：

```text
專案根目錄/
│
├── index.html
│
├── assets/
│   ├── images/
│   │   ├── weather/
│   │   │   ├── sunny/
│   │   │   ├── cloudy/
│   │   │   ├── rain/
│   │   │   ├── thunderstorm/
│   │   │   ├── typhoon/
│   │   │   ├── fog/
│   │   │   ├── strong-wind/
│   │   │   └── cold-wave/
│   │   │
│   │   └── clouds/
│   │
│   └── icons/
```

### 命名規則

- 檔案名稱使用小寫英文。
- 多個英文單字使用連字號 `-` 分隔。
- 圖片名稱應能辨識對應的天氣或雲種。
- 避免使用 `new1`、`test2`、`final-final` 等不具意義的名稱。
- 圖片應放在對應的資料夾，不要全部堆放在根目錄。

以上為未來擴充時的建議結構，不代表目前已經建立這些資料夾。

## 8. AI 修改或新增內容時的規則

AI 在修改本專案時，必須遵守以下原則。

### 8.1 修改前先理解現有程式碼

- 先確認目前檔案結構及使用方式。
- 了解相關函式與資料欄位。
- 確認修改是否會影響其他頁面。
- 不要只根據函式名稱推測功能。

### 8.2 保留原有功能

除非使用者明確要求，否則不可刪除或破壞：

- 首頁及八種天氣分類。
- 天氣介紹六個章節。
- 章節目錄及直接跳轉功能。
- 上一頁及下一頁切換。
- 左右滑動操作。
- 頁數顯示。
- 雲種圖鑑。
- 手機響應式排版。

新增功能時，應盡量以擴充原有程式碼的方式完成。

### 8.3 修改範圍

- 優先進行必要且最小幅度的修改。
- 不要在沒有需求的情況下重寫整份程式碼。
- 不要任意更換技術架構或引入大型框架。
- 不要擅自新增登入、資料庫、API、搜尋、收藏或測驗等功能。
- 不要更改與本次需求無關的版面及互動方式。
- 不要隨意修改既有函式名稱、資料欄位及 DOM 結構。

### 8.4 新增內容

- 新增天氣時，必須符合既有六章節結構。
- 新增雲種時，必須符合現有圖鑑資料格式。
- 新增圖片時，應使用合理的相對路徑。
- 新增文字時，應維持繁體中文及原有科普語氣。
- 新增內容後，確認首頁分類、閱讀頁面及圖鑑都能正常顯示。

### 8.5 氣象知識正確性

這是本專案最重要的內容規範之一。

- 優先使用中央氣象署、世界氣象組織及其他可信賴的氣象資料。
- 不可將可能出現的現象描述成必然發生。
- 不可將單一雲種當成確定天氣的依據。
- 不同天氣的形成機制可能不同，不可套用同一套變化流程。
- 氣壓、溫度、濕度及風向的變化應依實際氣象條件解釋。
- 晴天、陰天屬於天氣狀態；颱風、寒流則涉及天氣系統或氣團，介紹時應適當區分。
- 濃霧應考慮近地面水氣凝結、露點、相對濕度及能見度等因素。
- 不確定的資訊應標示為可能情況，不可自行編造數據或研究結論。

### 8.6 程式碼品質

- 保持原有程式碼風格。
- 避免重複撰寫相同功能。
- 確保新增函式名稱具有明確意義。
- 避免不必要的全域變數。
- 確認 JavaScript 沒有語法錯誤。
- 確認資料格式與畫面渲染邏輯相容。
- 確認圖片路徑及引用資源有效。
- 確認桌面及手機版面沒有明顯錯位。

### 8.7 修改完成後的檢查

每次修改完成後，至少檢查：

1. 首頁能否正常顯示。
2. 八種天氣分類是否完整。
3. 各天氣介紹頁是否能正常開啟。
4. 六個章節是否能正常切換。
5. 章節目錄是否能正確跳轉。
6. 左右滑動及上一頁、下一頁是否正常。
7. 雲種圖鑑是否能正常顯示。
8. 圖片是否正確載入。
9. 手機版是否能正常閱讀。
10. 是否意外影響其他既有功能。

## 9. 專案開發總原則

本專案以「簡單、清楚、容易閱讀、方便維護」為主要方向。

AI 在協助開發時，應優先考量：

1. **內容正確性**：氣象知識必須合理且有可靠依據。
2. **架構一致性**：新增內容應沿用既有資料及頁面結構。
3. **操作一致性**：不同天氣介紹頁應維持相同的閱讀操作方式。
4. **視覺一致性**：維持藍、白、淺灰色系及現代氣象資訊風格。
5. **簡潔性**：避免不必要的功能及過度複雜的技術。
6. **可維護性**：修改時盡量保留原有程式碼，避免影響其他功能。

任何較大幅度的架構調整、功能新增或視覺風格變更，都應先確認使用者的需求，不可自行擴大開發範圍。
